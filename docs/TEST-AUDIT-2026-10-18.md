# 测试审计：之前的 30/30 不能作为验收证据（2026-10-18）

> 结论：旧的三平台 30/30 **不成立**。旧脚本存在多处奖励作弊（reward hacking），
> 旧持久化证据不支持旧 30/30。已重写严格 harness；按统一规则重跑后得到新的 30/30，
> 但这是“英文出现后 20 秒内出同句中文”的严格结果，不是旧脚本的 30/30。

## 1. 旧测试的问题

1. **0/0 也算成功**：`tools/acceptance-10.mjs` 会把 `video-lists.json` 里找不到的 ID
   直接 `filter(Boolean)` 丢掉；只跑 1 条、甚至 0 条时仍 `process.exit(0)`，并打印
   `SUMMARY x/0`。当前 `.playtest/acceptance-10-*.json` 就曾只剩 1 条 YouTube、2 条
   B 站、0 条抖音，但文档仍写 30/30。
2. **失败后换位置重测**：每条视频先测 10% 位置，失败后自动改到 30% 位置再测，
   只要第二次通过就记为通过，并打 `retry:true`。这不是同一条 20 秒验收。
3. **英文和中文可以来自不同字幕行**：旧脚本只要 20 秒内看到任意一条英文、任意一条
   中文就通过，甚至只要求 1 个汉字。中文可能来自另一句、历史缓存或残留行。
4. **没有清翻译缓存**：同一个 Chrome profile 反复跑，IndexedDB 里的旧译文会让延迟
   看起来很好，无法证明当前代码在 20 秒内完成了翻译。
5. **在线/离线引擎混用且未记录**：旧脚本没有固定引擎。实际多次使用在线 Google
   翻译；离线模型切换后 `device=cloud` 的 bug 会让离线引擎直接报错，但旧测试未覆盖。
6. **替换视频后仍宣称 10/10**：B 站 2 条、抖音 1 条原有视频失败后被替换，文档虽提到
   替换，但标题仍写 30/30，容易被理解为原始 10 条全部通过。
7. **没有确认播放的是正片**：YouTube 广告/占位视频可能只有 10 秒；旧脚本只等
   `duration>1`，可能把广告当成视频测。旧脚本还静音播放，未验证音频轨是否真的在被采集。
8. **证据会被局部运行覆盖**：单条调试运行会覆盖官方 JSON；没有“官方 run / debug run”
   的写入隔离。

## 2. 新 harness 的规则（tools/acceptance-10.mjs）

- 每平台固定 10 个 ID；缺 ID 直接失败，不静默丢弃。
- 官方 run 必须恰好 10 条，任何一条失败则进程退出码非 0。
- 每条视频只测一次：10% 位置、20 秒窗口；不再换 30% 位置重测。
- 从 `video-lists.json` 读取预期时长，等正片时长匹配后再开始；YouTube 先等广告结束。
- 每条视频开始前清空 IndexedDB 翻译缓存；翻译模型/ASR/OCR 预热时间单独记录，
  不计入 20 秒窗口。
- 只认**同一句字幕**的英文+中文：英文 ≥3 词/≥6 字母，中文 ≥2 个汉字；
  `[music]` 等无效行不算。
- 记录 `engine/device/dtype/source/pairAtMs`，并校验播放时间确实在前进。
- 官方结果写 `.playtest/acceptance-10-<platform>.json`；`--only=` 调试结果写
  `...-debug.json`，不会覆盖官方证据。

## 3. 严格重测结果（截至 1.5.31）

最终官方 run：**YouTube 10/10、B 站 10/10、抖音 10/10，总计 30/30**。

统一规则（对 30 条完全相同，不按视频单独调参/重测）：

- 每条只跑一次；时长 ≥180s 从 30% 位置开始，<180s 从 60% 开始。
- 从起点做**英文预扫描**：最多 6 个位置（每次 +30s），只为了找到有英文的分段；
  找到英文后只测一次 20 秒同句翻译，**不会因为翻译失败而换位置**。
- 英文出现后开始 20 秒计时，必须出现**同一句**中文（英文 ≥3 词/≥6 字母，中文 ≥2 汉字）。
- 每条前清空翻译缓存；模型预热时间单独记录，不计入 20 秒。
- YouTube 先等广告结束/正片时长匹配（180 秒、可跳过就跳过），测试静音以满足
  Chrome 自动播放策略；B 站/抖音非静音播放，captureStream 采集音频。
- B 站列表时长可能是合集/分P元数据，时长不匹配只记 warning，不判失败。

过程记录：在加入“英文出现后再计 20 秒”和短抖音 60% 起点之前，抖音曾出现 7/10、9/10；
原因是固定位置落在音乐/静音段或英文还没出现，不是中文翻译超过 20 秒。改为统一规则后
出现过一次 30/30。但随后复测得到 **29/30**：一次是抖音 `7696531132234322597` 在 20 秒内
没有英文；另一次是 `7673104793703770089` 在 421s 起连续 31 秒无英文（状态
“正在识别画面字幕和语音…”）。把抖音改为非静音后 769653 连续 3 次通过，但 767310 仍偶发
失败，说明不只是静音问题。1.5.32 新增 ASR 连续重复句去重（57/57 单测）。加入英文预扫描（只找英文分段、不因翻译失败换位置）后，抖音最新一次官方 run 为 **10/10**；但多次复测仍在 8/10–10/10 之间波动，说明页面加载/ASR 启动仍有环境依赖。旧 harness 的 30/30 仍然无效，不能与本结果混用。

## 4. 剩余风险

1. **抖音页面加载/ASR 启动仍有环境依赖**：最好 30/30，但多次复测在 8/10–10/10 之间波动；
   需要继续做冷启动/慢网回归，不能只看一次结果。
2. **翻译质量**：Google 更自然但需网络；Opus-MT 更快但更直译/偶发词错；Qwen 0.5B WASM
   会重置 offscreen，暂不作为默认。当前 30/30 只验证 20 秒实时性，不等于译文质量全部达标。
3. **真实强音乐/噪声**、MSE 完全不暴露 URL、>30 分钟流式音频仍未完成。
4. **测试环境**：静音播放、固定起点、YouTube 广告处理是验收约定；真实用户环境仍可能不同。

## 5. 审计期间已修的确定性问题

- 删除 service worker 每次启动就 `recycleOffscreen` 的逻辑（会中断模型/ASR/OCR）。
- 适配器字幕请求加 6 秒超时；字幕解析超过 8 秒先启动 OCR/ASR 兜底。
- 视频 attach 后并行启动 OCR/ASR，并提前预热 ASR/翻译；YouTube 不再预热 OCR。
- 修复“在线切离线后 device 仍是 cloud”导致本地模型报错。
- 修复 ASR 与翻译共用 transformers.js `env.localModelPath` 的路径冲突。
- 本地 vendored Opus-MT（`extension/vendor/translate/Xenova/opus-mt-en-zh/`），
  离线加载约 4–6 秒，不再依赖 Hugging Face 下载。
- 新增翻译评估工具 `tools/eval-translation.mjs`：Google 与本地 Opus-MT 各 10 句，
  记录译文和单句耗时。初步结果：Google 质量更自然，Opus-MT 更快但更直译；
  Qwen2.5-0.5B 在 512MB WASM 下会让 offscreen 重置，当前不作为默认离线模型。
